Фундаментальные контракты и структуры хранения данных

1. Контракт: Изменяемая упорядоченная карта (MutableOrderedMap).
Это абстракция отсортированного хранилища ключ-значение в памяти, позволяющая изменять содержимое. Контракт определяет базовые операции: вставка, поиск, удаление и обход в отсортированном порядке. На языке Go такой контракт можно описать интерфейсом:

type MutableOrderedMap[K comparable, V any] interface {
    Put(key K, value V)           // вставка или обновление значения по ключу
    Get(key K) (V, bool)          // поиск значения по ключу
    Delete(key K) bool            // удаление ключа (возвращает true, если ключ был)
    Iterator() OrderedIterator[K, V] // итерирование по отсортированным ключам
}


Все реализации этого интерфейса должны гарантировать логическую упорядоченность элементов (по возрастанию ключей) и определённую асимптотику операций. Атомарными шагами в оценке сложности здесь будем считать сравнения ключей и переходы по указателям (для структур в памяти).

2. Реализация контракта: Skip List (скип-список).
Skip List – вероятностная структура данных, обеспечивающая быстродействие, сравнимое с сбалансированным деревом, но более простая в реализации. Она широко используется в качестве Memtable в LSM-деревьях. В skip list элементы хранятся в отсортированном однонаправленном списке, поверх которого строятся несколько уровней «ускоренных» списков для быстрого пропуска длинных цепочек. Каждый элемент случайно продублирован на некотором числе верхних уровней, что обеспечивает в среднем логарифмическое время операций.

Структура данных (псевдокод на Go):

type skipListNode[K, V any] struct {
    key   K
    value V
    next  []*skipListNode[K, V]  // массив ссылок на узлы на каждом уровне
}

type SkipListMap[K comparable, V any] struct {
    head     *skipListNode[K, V] // голова списка (минimalный ключ)
    maxLevel int                 // максимальный уровень (высота списка)
    p        float64             // вероятность поднятия на следующий уровень (например 0.25)
    level    int                 // текущая высота (уровень самых верхних элементов)
}


Операция поиска выполняется, начиная с верхнего уровня и спускаясь вниз: на каждом уровне мы движемся по next пока следующий узел не превысит искомый ключ, затем спускаемся на уровень ниже. Псевдокод поиска:

func (m *SkipListMap[K, V]) Get(key K) (V, bool) {
    x := m.head
    // начинаем с самого верхнего уровня и постепенно спускаемся
    for level := m.level - 1; level >= 0; level-- {
        for x.next[level] != nil && x.next[level].key < key {
            x = x.next[level]  // пролистываем элементы на текущем уровне
        }
    }
    // на нижнем уровне проверяем текущий следующий элемент
    x = x.next[0]
    if x != nil && x.key == key {
        return x.value, true
    }
    return *new(V), false  // не найдено
}


Операция вставки сначала находит позицию через такой же поиск, затем вставляет новый узел на нижнем уровне, после чего с фиксированной вероятностью «поднимает» его на следующий уровень, повторяя процесс, пока случай не прервёт или достигнут maxLevel. Удаление аналогично — находится элемент и убирается с каждого уровня.

Асимптотика Skip List: В среднем случае все основные операции – Put, Get, Delete – выполняются за O(log n) шагов, где n – число элементов. Это количество шагов измеряется числом сравнений ключей и переходов по указателям. В худшем случае (маловероятном, если генерация уровней неудачна) операции могут деградировать до O(n), однако при хорошем выборе параметра p вероятность этого крайне мала. На практике skip list обеспечивает близкое к логарифмическому время даже при миллионов элементов.

Почему Skip List для Memtable: Он не требует сложных операций балансировки (в отличие от деревьев, где нужны вращения), прост в реализации и хорошо показывет себя в однопоточной записи. В то же время, другие структуры также могут реализовать MutableOrderedMap.

Альтернативная реализация: Сбалансированное бинарное дерево. Классический пример – красно-чёрное дерево или AVL-дерево. Эти структуры также дают O(log n) на Get/Put/Delete в худшем случае за счёт строгой балансировки. Многие языки (Java TreeMap, C++ std::map) используют красно-чёрные деревья для упорядоченных словарей. В контексте LSM-деревьев часто выбирают Skip List вместо деревьев, чтобы упростить код базы данных: вставки в skip list не блокируют глобальные структуры для вращений, а поиск может быть немного более последовательным по памяти. Тем не менее, с точки зрения контракта MutableOrderedMap, сбалансированное дерево и skip list эквивалентны по функциональности и сложности операций (оба дают порядка O(log n) шагов).

3. Реализация: Bloom Filter (вероятностное множество).
Bloom Filter не реализует интерфейс карты, но представляет отдельный контракт: хранение множества с однонаправленной ошибкой (false positive). Его можно рассматривать как контракт ProbabilisticSet с операциями Add(element) и Check(element) bool. Цель – очень дёшево по памяти и времени определить, может ли элемент присутствовать в наборе, допуская небольшое процент ложных срабатываний, но никогда не пропуская существующий элемент.

Основные операции Bloom Filter и их эффективность:

type BloomFilter struct {
    bitset   []uint8     // битовый массив
    k        int         // число хэш-функций
    hashFuncs []func(data []byte) uint32  // набор независимых хэш-функций
}

func (bf *BloomFilter) Add(key []byte) {
    for i := 0; i < bf.k; i++ {
        idx := bf.hashFuncs[i](key) % uint32(len(bf.bitset)*8)
        // устанавливаем соответствующий бит в битовом массиве
        bf.bitset[idx/8] |= (1 << (idx % 8))
    }
}

func (bf *BloomFilter) Check(key []byte) bool {
    for i := 0; i < bf.k; i++ {
        idx := bf.hashFuncs[i](key) % uint32(len(bf.bitset)*8)
        if (bf.bitset[idx/8] & (1 << (idx % 8))) == 0 {
            return false  // хотя бы один бит не установлен -> ключ точно отсутствует
        }
    }
    return true  // все биты установлены -> ключ, возможно, присутствует
}


Время работы: обе операции Add и Check требуют k вычислений хэш-функций и установок/проверок битов, то есть сложность O(k), где k – количество хэшей (обычно 3-10). Это константное время относительно числа элементов в фильтре, если считать единицей работы одну хэш-функцию и обращение к биту.

Ложные срабатывания: вероятность false positive (когда Check возвращает true для элемента, которого нет) примерно равна $(1 - e^{-k n/m})^k$, где n – число добавленных элементов, m – количество бит в битовом массиве. На практике параметры выбираются так, чтобы эта вероятность была очень низкой (1-2%). Ложных отрицаний не бывает: если элемент был добавлен, Check гарантированно не вернёт false.

Память: фильтр экономит память – требуется лишь несколько бит на элемент (обычно 8-12 бит на элемент для заданной ошибки), что значительно компактнее, чем хранить сами ключи или отдельный флаг наличия.

Применение: Bloom Filter обычно используется вместе с основной структурой хранения (например, SSTable) для быстрой фильтрации запросов на отсутствие. Перед тем как делать дорогостоящий поиск на диске, мы проверяем Bloom Filter: если он говорит "элемента нет", можно сразу избежать ввода-вывода.

4. Реализация: SSTable (Sorted String Table — отсортированная строковая таблица).
SSTable – это иммутабельная (неизменяемая после создания) структура на диске, хранящая отсортированные пары ключ-значение. Её контракт можно представить как ImmutableOrderedMap: есть операции чтения (Get по ключу, итерация по диапазону), но нет прямых операций записи или удаления (новые данные добавляются только созданием новых SSTable). SSTable лежит в основе LSM-дерева как конечное хранилище данных на диск.

Внутреннее устройство SSTable: данные хранятся в файле, разбитом на блоки фиксированного размера (порядка 4 КБ). В файле обычно располагаются:

Data Blocks: основная масса данных, разбитая на блоки. Внутри блока записаны отсортированные пары [key, value] (сжатые по ключу для экономии места) и могут быть специальные точки перезапуска (restart points) для ускорения бинарного поиска внутри блока. Каждый блок может заканчиваться контрольной суммой.

Index Block: индекс, содержащий для каждого блока минимальный ключ в нём и смещение этого блока в файле. Индекс сам может быть небольшим и часто целиком помещается в память при открытии файла.

Metadata / Filter Block: дополнительная информация – например, здесь хранится Bloom Filter для всех ключей этого файла, а также другие метаданные (минимальный/максимальный ключ, количество записей и т.д.).

Footer: в конце файла фиксированная структура с указателями на начала Index Block и Metadata Block для быстрой навигации, плюс magic number для проверки формата.

Операция поиска (Get) в SSTable:

Bloom Filter (опционально): Если для SSTable загружен Bloom Filter, сначала выполняется bf.Check(key). Если он вернул false, значит ключа точно нет и можно сразу завершить поиск. Если true – ключ может быть, и нужно продолжить. (Сложность: ~O(k) на несколько хешей в памяти.)

Поиск по индексу блоков: выполняем бинарный поиск по массиву индексных записей (ключей) в памяти, чтобы найти блок, который может содержать искомый ключ. Мы сравниваем искомый ключ с последними ключами каждого блока. В результате находим нужный блок и узнаём его смещение в файле. (Сложность: O(log B) сравнений, где B – число блоков в файле. Обычно B невелик, порядка сотен или тысяч, поэтому это очень быстро.)

Чтение блока с диска: выполняем одно дисковое чтение нужного блока (например, 4 KB). Это основная стоимость по времени, так как обращение к диску – миллионы инструкций по эквиваленту.

Поиск внутри блока: внутри блока данные уже отсортированы по ключам. Можно выполнить бинарный поиск по ключу внутри блока или линейный проход (поскольку блок небольшой, линейный поиск часто достаточно быстрый). Находим запись с искомым ключом или убеждаемся, что её нет. (Сложность: O(k) операций, где k – число записей в блоке; обычно это до нескольких десятков или сотен записей.)

Таким образом, чтение из SSTable в худшем случае требует 2 обращения к диску (один за индексом, если он не в памяти, и второй за соответствующим блоком) и выполняет порядка O(log B + k) операций в памяти (поиск по индексу и внутри блока). На практике индекс часто кешируется, поэтому обычно достаточно одного чтения блока.

Диапазонный запрос (range scan) в SSTable очень эффективен: достаточно найти начало диапазона по индексу (как при Get), а затем последовательно читать блок за блоком. Последовательные чтения по файлу близки к оптимальной пропускной способности диска, что делает SSTable отличной структурой для сканирования больших отсортированных диапазонов данных.

5. Построение систем из этих компонентов.
Теперь, имея базовые «кирпичики» — изменяемую отсортированную карту в памяти (Memtable), иммутабельную отсортированную таблицу на диске (SSTable) и фильтр Bloom для отсеивания отсутствующих ключей — можно понять архитектуру крупных структур хранения.

LSM-дерево (Log-Structured Merge Tree): это не отдельная структура, а комбинация компонентов, организованных для оптимизации записи. LSM-дерево использует MutableOrderedMap в памяти (Memtable) для приёма всех записей. Обычно это Skip List (обеспечивающий логарифмические вставки). Каждая операция записи также журналируется в WAL (Write-Ahead Log) — простой append-only лог на диске для долговечности. Когда Memtable заполняется (достигает порога по объёму), она замораживается (преобразуется в иммутабельную структуру) и асинхронно сбрасывается на диск в виде нового SSTable-файла. После сброса старый memtable становится постоянным файлом, а активной становится новая пустая Memtable. Со временем накапливается много SSTable-файлов, и для поддержки эффективности чтения выполняется компакция – слияние нескольких SSTable в один более крупный (при этом удаляются дубликаты и tombstone-пометки удалений). Компакция происходит на разных уровнях, как описано ранее (L0, L1, L2,... с увеличивающимся размером). Для ускорения поиска по нескольким SSTable, каждый SSTable снабжается Bloom Filter-ом, благодаря которому большинство запросов к несуществующим ключам не доходят до диска.

Как выполняются операции:

Put/Update (запись): записывается в WAL (последовательное добавление – O(1) по диску), затем вставляется в Memtable (O(log n) по числу элементов в памяти). Если Memtable переполнена, она отправляется на диск (операция ~O(n) для сортировки/записи, но это происходит редко и асинхронно, амортизированно для единичной вставки это всё равно O(1)). Таким образом, с точки зрения интерфейса, Put возвращает быстро, не дожидаясь полной записи на диск.

Get (чтение): сначала ищется в текущей Memtable (O(log n) в памяти). Если не найдено, просматриваются замороженные иммутабельные Memtable (если они ещё не сброшены) – обычно их немного, тоже логарифмический поиск. Далее проверяются SSTable-файлы по уровням: сначала самые новые на L0, затем глубже. Bloom Filter перед чтением каждого SSTable зачастую сразу подсказывает, что внутри файла ключа нет (это очень дешевая проверка в памяти ~O(k)). Если Bloom даёт положительный ответ, выполняется поиск в SSTable: одна-две операции чтения с диска и несколько логарифмических шагов в памяти, как описано выше. LSM-дерево может иметь несколько версий одного ключа (в разных файлах разных уровней), поэтому всегда возвращается самая свежая версия (для этого порядок обзора – от свежих файлов к старым). Амортизированно число SSTable, которые нужно проверить, ограничено параметрами системы (например, L0 содержит не более N файлов, на каждом следующем уровне данные размазаны, так что на запрос обычно приходится читать лишь 0 или 1 SSTable на уровень после фильтрации Bloom Filter-ами). В итоге стоимость чтения – примерно O(log n + L · (k + log B)), где L – количество уровней (обычно 2-3 затрагиваются). В среднем случае большинство файлов отсекается Bloom Filter-ами, и чтение похоже по затратам на B-дерево (несколько дисковых блоков).

Delete (удаление): реализуется как особая запись "tombstone" в Memtable (Put(key, TOMBSTONE)). Это метка, что ключ удалён. Она тоже пойдёт в WAL и затем в SSTable при сбросе. Пока старые версии данных находятся в более старых SSTable, запрос Get будет встречать tombstone раньше их по времени и знать, что пользователь удалил запись. Окончательное удаление происходит при компакции: tombstone объединяется с более старыми данными и вместе они выкидываются. Таким образом, с точки зрения клиента, Delete работает как Put (почти мгновенно), но физическое освобождение места откладывается.

Почему это работает эффективно: Записи сначала накапливаются и сортируются в памяти, благодаря чему диск всегда пишется последовательно крупными блоками (целыми SSTable файлами), избегая медленных случайных записей. Компакции также стараются чередовать последовательное чтение и запись большими частями. Чтения же, хоть и сложнее, чем в B-дереве (нужно проверить несколько мест), компенсируются большим использованием памяти: все актуальные данные недавних записей в Memtable, индексы и фильтры в памяти, плюс дисковые обращения сгруппированы. LSM-дерево особо выигрывает в сценарииях, где количество записей огромное, а запись идёт непрерывно (например, логи, метрики) – оно справляется с нагрузкой вплоть до сотен тысяч операций ввода-вывода в секунду, амортизируя затраты на сортировку и слияние.

B-дерево: в отличие от LSM, это более монолитная структура – единое дисковое дерево, которое само по себе реализует контракт MutableOrderedMap (хотя обычно B-дерево используется как immutable index для данных, хранящихся отдельно, или как индекс-с-пойнтерами на записи). B-дерево не требует дополнительных компонентов вроде фильтров или компакций: оно поддерживает баланс за счёт разделения узлов. Однако за это приходится платить сложностью операций модификации: вставка или удаление в B-дереве может приводить к чтению и перезаписи нескольких узлов на диске (чтение узла, изменение, запись обратно), а при переполнении – к разделению узла, что затрагивает и родительский узел (вплоть до корня). В итоге вставки/удаления в B-дереве хотя и имеют асимптотику O(log n) по числу операций, но каждая такая операция включает несколько случайных дисковых I/O (несколько отдельных блоков). LSM подменяет многие случайные записи последовательными, жертвуя простотой чтения. Таким образом, выбор структуры – это компромисс: B-дерево обеспечивает более предсказуемое и быстрое чтение (ключ обычно находится за O(log_B N) дисковых обращений, где B – вместимость узла, а N – число записей), а LSM-дерево обеспечивает более быструю массовую запись и меньшую амортизацию диска за счет серийных операций слияния. В современных СУБД часто применяются оба подхода: классические реляционные базы используют B+-деревья для индексов, а BigTable-подобные хранилища (Cassandra, HBase, ClickHouse MergeTree) используют LSM-структуры под капотом.
